## 2026-09-27 — [M2] 발화 길이를 모델에 알려주는 방식(SpeakerCNNLargeWithDuration) 최종 기각 — 다시 확인해보니 예전 개선 효과가 없었음

- **현황**: M2-CNN-004(2026-09-16)에서 정확도가 +0.30%p 좋아졌다고 봤던 결과(대신 격차는 더
  벌어짐)가, 사실은 실행할 때마다 모델 초기값과 데이터 섞는 순서를 고정하지 않아서 생긴 우연일
  수 있다는 게 M2-CNN-005(hop80 실험)를 다시 들여다보는 과정에서 같이 드러남. 그래서
  `train_mission2_cnn.py`에 `--torch-seed`(모델 초기값 + 데이터 섞는 순서를 고정하는 값,
  데이터를 나누는 seed와는 다름)를 추가하고, M2-CNN-004를 이 값 1/2/3으로 3번 다시
  확인함(M2-CNN-006).
- **결과**: 전체 정확도 차이(발화 길이를 알려주는 모델 − 기존 모델) 평균 -0.15%p, **3번 다
  마이너스** — 예전과 반대 방향. 원래 목표였던 0.5~1초 발화 구간도 3번 다 -0.39%p~-0.95%p로
  나빠짐(평균 -0.70%p, 같은 모델을 반복 실행했을 때 원래 생기는 편차인 0.15~0.17%p보다 뚜렷이
  큼) — 발화 길이 정보를 알려주는 게 오히려 이 구간에는 방해가 될 수 있다는 신호. <0.5초 구간은
  좋아졌다 나빠졌다 해서 판단 불가.
- **결정**: 이 방식(SpeakerCNNLargeWithDuration)은 쓰지 않는다. M2-CNN-004의 예전 수치는
  무효로 처리한다. M2-CNN-005(hop80)를 기각했던 이유("실행마다 결과가 흔들려서 믿을 수 없다")도
  이번에 다시 확인됨 — 두 실험 다 실제로 효과가 있었던 게 아니라, 한 번만 실행해본 결과를 진짜
  효과로 착각했던 것.
- **이유**: 지난 세션에서 "대회 채점이 정확도 하나만 보니까, 격차가 벌어져도 정확도만 보고
  다시 판단하자"고 했던 논리 자체는 맞았지만, 실제로 다시 재봤더니 그 정확도 개선 자체가
  우연이었다. "다시 판단해볼 이유가 있다"는 것과 "다시 판단해보니 진짜 좋다"는 것은 서로 다른
  문제였다.
- **후속 조치**: `--torch-seed`는 앞으로 이런 비교를 할 때 기본으로 쓴다(한 번만 실행한 결과를
  그대로 믿지 않는다). 0.5~1초 발화 구간 문제는 다른 방법(소리를 이미지로 바꿀 때 주파수 쪽
  해상도를 높이는 것, 짧은 발화를 학습에 더 자주 보여주는 것 등)을 다음으로 검토한다.
- **관련**: M2-CNN-004, M2-CNN-005, M2-CNN-006(`docs/experiment_log.md`),
  [`m2_cnn_duration_seed_recheck.md`](../reports/mission2/m2_cnn_duration_seed_recheck.md).

- **후속 조치**: `mission2_inference.py`에 L1/L2 둘 다 되게 만드는 작업(또는 L2 전용 스크립트를

- **관련**: M2-AUDIT-003, M2-VAL-002, M2-VAL-003(`docs/experiment_log.md`).

## 2026-09-23 — [M2] L1·L2를 발화 단위로 비교 — L2가 잘하는 이유(겹침·짧은 발화) 확인, L2 쓰기로 한 결정 유지

- **현황**: 바로 아래(2026-09-23) 결정에서 "나중에 확인하기"로 남겨뒀던 것 — L1이 못 맞히는 걸
  L2가 맞히는지, 반대인 경우는 없는지 발화 하나하나 단위로 비교(M2-COMPARE-002)를 끝냄.
- **결과**: 목소리가 겹치는 구간(48,863개)에서 L1 81.83%→L2 88.88%(+7.05%p)로, 안 겹치는
  구간의 +2.43%p보다 훨씬 크게 좋아짐 — L2가 잘하는 이유가 겹친 목소리를 스펙트로그램으로 더 잘
  구분해내기 때문으로 보임. 발화 길이별로도 전 구간에서 L2가 낫고 0.5~2초 짧은 발화에서 차이가
  제일 큼. 두 모델이 같이 맞았는지 비교해보면, L2가 L1의 오답을 고치는 경우(7,198건)가 반대로
  L2가 새로 틀리는 경우(2,224건)보다 약 3.2배 많음 — L1에서 L2로 바꾸는 게 방향성 있는 개선이란
  뜻. 둘 다 틀리는 7,980건은 여전히 못 풀었음.
- **결정**: 위 2026-09-23 "L2 쓰기로 한 결정"을 그대로 유지한다. 이번 분석에서 반대 근거는 안
  나왔고, 오히려 L2가 왜 잘하는지(겹침·짧은 발화 처리)만 더 뚜렷해짐. 코드는 안 바꾼다. 둘 다
  틀리는 7,980건이나 두 모델을 합치는(앙상블) 방법은 지금 당장 급하지 않은 추가 개선 여지로만
  남겨두고, 제출 일정에 여유가 있으면 나중에 판단한다.
- **관련**: M2-VAL-002, M2-VAL-003, M2-COMPARE-002(`docs/experiment_log.md`),
  [`m2_l1_l2_official_validation_comparison.json`](../reports/mission2/m2_l1_l2_official_validation_comparison.json).

## 2026-09-23 — [M2] L2(CNN) 공식 Validation 확정 — L1보다 훨씬 좋아서 제출 우선순위를 L2로 바꿈

- **현황**: 2026-09-18에 "L1을 먼저 완성하고 L2는 잠깐 미루자"고 정하면서 남겨뒀던 조건 4개 —
  (1) hop-length 실험, (2) `mission2-l2-cnn-clean`에 라벨 수정 반영, (3) 공식 Validation 1회
  확인, (4) 팀 공용 main에 합칠지 결정 — 중 (2)·(3)이 이번에 끝남. (1)은 아직 안 함.
- **결과**: L2(SpeakerCNNLarge, 라벨 수정 반영해서 재학습)를 공식 Validation으로 평가한 결과
  **90.88~90.89%**(M2-VAL-003) — 같은 시점 L1 최종 후보(M2-VAL-002, 86.44%)보다
  **+4.44~4.45%p 높음**. 다른 팀들 기록 중 제일 높았던 것(eunkyo00, 90.25%)보다도 높음 —
  지금까지 확인된 것 중 최고 기록.
- **인프라 메모**: 내 컴퓨터(CPU)로 111,947개 발화를 처리하는 게 너무 느려서(파일을 하나씩
  OneDrive 폴더에서 읽는 구조) Colab GPU로 옮겨서 돌림. 같은 저장 모델(21번째 학습)을 CPU/GPU
  양쪽에서 평가해보니 정확도는 거의 같은데(90.89%/90.88%), 계산 방식 차이로 약 250건(전체의
  0.22%)의 개별 예측이 서로 달랐음 — 정답 기준선(0.5) 바로 근처에 있던 애매한 케이스들로
  추정되고, 결론에는 영향 없음.
- **결정**: (4) 팀 공용 main에 합칠지를 지금 정한다 — 제출 우선순위를 L2로 바꾼다. L1(86.44%)은
  안정적인 대안/비교용으로 남겨두고, 앞으로 정확도 개선 작업은 L2 쪽에 집중한다. (1) hop-length
  실험은 이미 차이가 크게 확인된 상태라 급하지 않음 — 여유 되면 낮은 우선순위로 추가 진행한다.
- **이유**: +4.4%p는 대회 채점(정확도 하나만 봄) 기준으로 매우 큰 차이이고, 2026-09-18에
  "L1이 정리하기 더 쉽다"고 판단했던 이유는 이제 L1이 다 끝났으니 더는 유효하지 않음. L2를 더
  미룰수록 손해만 커짐(2026-09-18 결정에서 이미 지적한 위험).
- **후속 조치**: `mission2-l2-cnn-clean`을 main에 합치기(팀원 검토 거쳐서, 본인이 직접 승인하는
  셀프 머지는 금지). L1 대비 L2가 어떤 발화를 더 잘 맞히고 못 맞히는지 발화 단위로 비교 진행 중.
- **관련**: M2-VAL-002, M2-VAL-003, M2-CNN-003(`docs/experiment_log.md`),
  [`m2_l2_official_validation_result_local_cpu.json`](../reports/mission2/m2_l2_official_validation_result_local_cpu.json),

## 2026-09-20 — [M3] 데이터 나누는 두 가지 방식 비교 필요 (아직 안 끝남)

- **현황**: [`mission3_baseline.py`](../scripts/mission3_baseline.py)는 통화(`recordId`)
  단위로 묶은 뒤 라벨 비율을 맞춰 나누고,
  [`mission3_baseline 최종 수정본.py`](<../scripts/mission3_baseline 최종 수정본.py>)는 JSON
  한 줄(발화)마다 바로 라벨 비율을 맞춰 나눔.
- **문제**: 수정본은 `recordId`를 따로 보존하지 않아서, 같은 통화가 중복돼 있으면 학습용과
  검증용에 같이 들어갈 수 있음. 반대로 모든 `recordId`가 겹치지 않는다면, 0.3955와 0.4530의
  차이는 데이터가 새는(리키지) 문제가 아니라 그냥 다르게 나눈 데서 온 우연한 차이일 수 있음.
- **함께 사라진 안전장치**: 원본 코드는 나눈 뒤에 학습용/검증용에 같은 `recordId`가 겹치는지
  검사해서, 하나라도 겹치면 바로 에러를 내며 멈추는데, 수정본에는 이 검사가 빠져 있음. 지금은
  겹치는 게 없더라도 데이터가 바뀌면 조용히 문제가 생길 수 있으니, 어느 쪽을 쓰든 이 검사는
  유지해야 함. 수정본은 발화를 시간 순서대로 정렬하는 것도 없앴는데, 지금 쓰는 방식(TF-IDF
  1~2단어 묶음)에는 영향이 작지만, 순서에 의존하는 모델로 바꾸면 시간순 정렬을 반드시
  되살려야 함.
- **결정**: 같은 데이터·모델·seed로 전체 행 수, 고유 `recordId` 수, 중복 그룹 수, 학습/검증
  겹침을 기록하고 통화 단위로 다시 나눠서 평가하기 전까지는 0.4530을 최종 수치로 인정하지
  않는다.
- **담당/완료 조건**: 이수빈 확인 요청. 나눈 방식의 검사 결과와 재실행 결과를 기계로 읽을 수
  있는 로그로 남기면 마무리.

## 2026-09-18 — [M2] L1을 먼저 끝내고 L2(CNN)는 잠깐 미룸

- **담당/완료 조건**: L2를 다시 시작할 때 확인할 것: (1) hop-length 실험 재학습/평가, (2)

  맞는다는 건 불확실성 계산 방법이 맞다는 교차 확인일 뿐이지, 데이터를 어떻게 나누든 모델이
  안정적이라는 증거로 쓰지는 않는다.
- **한계/후속**: 지금 결과는 데이터를 나누는 방식에 따라 얼마나 흔들리는지는 확인 안 한 상태다.
  최종 모델을 정하기 전에 필요하면 반복 holdout, k-fold, 또는 쌍(paired) 비교를 한다.

## 2026-09-10 — [M1] "통계적으로 동급"이라는 표현 수정 (외부 리뷰 반영)

- **결정**: PR 설명과 verdict에 있던 "두 모델 신뢰구간이 겹쳐서 통계적으로 동급"이라는 표현을
  "차이가 작음(0.19%p)"으로, "과적합·데이터 누수 징후 없음"을 "뚜렷한 징후는 관찰되지 않음"으로
  고침.
- **이유**: GBM과 LR은 같은 3,640개 샘플을 놓고 비교한 것(paired comparison)이라, 각 모델의
  신뢰구간이 겹친다는 것만으로는 통계적으로 같다고 말할 수 없음. 제대로 비교하려면 McNemar
  검정이나 paired bootstrap 같은 방법이 필요함.
