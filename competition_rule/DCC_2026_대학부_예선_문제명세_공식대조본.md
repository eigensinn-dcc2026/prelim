# DCC 2026 대학부 예선 문제 명세


## 1. 문제 개요

### 1.1 문제명

**전화대화 음성 및 전사 데이터를 이용한 응급상황 인식**

### 1.2 목표

> 음성 및 전사 등 발화 분야 내 광범위한 기술 스택을 이용하여 사회안전이라는 문제를 해결함.

### 1.3 사용 데이터셋

- AI-Hub **「위급상황 음성/음향(고도화) - 119 지능형 신고접수 음성 인식 데이터」**
- 데이터 유형: 오디오, 텍스트
- 구축년도: 2023
- 갱신년월: 2024-10
- 슬라이드에 표시된 용량: 87.29 GB
- 슬라이드에 표시된 조회수: 25,873
- 슬라이드에 표시된 다운로드 수: 1,122

위 수치는 발대식 당시 슬라이드에 삽입된 AI-Hub 화면의 표시값이며, 실제 대회 배포본의 크기나 구성과 같다는 뜻은 아니다.

### 1.4 데이터 구성

- 음성 파일: `.wav`
- 전사 및 annotation 파일: `.json`
- 음성과 JSON 파일명은 동일한 식별자와 날짜를 공유하는 형태로 보인다.
- JSON 예시 화면에는 다음과 같은 필드가 표시되었다.
  - `mediaType`
  - `gender`
  - `address`
  - `disasterLarge`
  - `disasterMedium`
  - `urgencyLevel`
  - `sentiment`
  - `symptom`
  - `triage`

단, 위 필드 전체를 모든 Mission의 입력으로 사용할 수 있는 것은 아니다. Mission마다 허용된 입력과 annotation이 따로 지정된다.

## 3. 공통 조건과 금지사항

### 3.1 데이터 및 도구 사용 조건

- 대회 데이터는 **AI-Hub 「위급상황 음성/음향(고도화) - 119 지능형 신고접수 음성 인식 데이터」 가공본만** 사용한다.
- 제공받은 데이터 중 각 Mission에서 지정하는 입력과 출력만 각각 입력과 출력으로 사용한다.
- 지정되지 않은 라벨링 데이터를 입력으로 사용하면 안 된다.
- 공개 오픈소스 라이브러리와 사전학습 모델의 사용은 허용된다.
  - Hugging Face 등에 공개된 Pre-trained 모델을 직접 다운로드하여 자체 환경에서 Inference 또는 Fine-tuning할 수 있다.
  - 공식 Q&A 예시: Qwen, LLaMA
  - 출제문제 슬라이드 예시: pre-trained ResNet50
- 외부 상용 AI API를 직접 호출하는 방식은 엄격히 금지된다.
  - 예: GPT, Claude, Google Vision, GPT-4o 등의 외부 API 호출

### 3.2 학습·검증 및 전처리 조건

- Training set으로는 서울 데이터만 사용한다.
- Validation 데이터는 평가와 개발 의사결정에 사용할 수 있다.
  - 모델 구조 및 하이퍼파라미터 선정
  - 최종 모델 선택
  - 앙상블 가중치 조정
  - 학습 중 주기적 평가를 통한 Early Stopping 및 Best Checkpoint 선정
  - Learning Rate Scheduler 트리거
- Validation 데이터를 Training set에 직접 편입하거나 Backpropagation에 사용하는 것은 금지되며, **실격 사유**이다.
- Sample instance마다 label에 따라 상이한 전처리를 적용할 수 없다.
- 평가 데이터에서만 유리한 특별 전처리를 적용할 수 없다.

### 3.3.1 공식 Q&A — Decision Threshold 기준 (주최 측 공지)

여러 팀의 문의에 따라 주최 측이 안내한 기준이다. 게시일은 원문 확인 후 기입한다. 이 기준은 아래 6.x/7.x의 임계값 관련 서술보다 우선한다.

**핵심 원칙**

> “확률값을 더 잘 예측하기 위한 모델 학습 및 calibration은 자유롭게 수행할 수 있으나, 최종 확률을 label로 변환하는 Decision Threshold는 항상 0.5로 고정한다.”

**Q1. Decision Threshold는 반드시 0.5로 사용해야 하나요?**

네. 최종 예측 확률을 label 0 또는 1로 변환할 때 사용하는 Decision Threshold는 Train / Validation 여부와 관계없이 **0.5로 고정**한다.

- prediction ≥ 0.5 → 1
- prediction < 0.5 → 0

**Q2. Validation set을 쓰지 않고 Train set에서 별도 subset을 나누어 Threshold를 찾는 것은 가능한가요?**

허용되지 않는다. Train set을 9:1 등으로 나누거나 OOF prediction을 활용하더라도, 그 결과로 최종 Decision Threshold를 0.4, 0.6 등 0.5가 아닌 값으로 조정하는 것은 동일하게 Threshold Tuning에 해당한다. Threshold를 결정하는 데이터가 Train인지 Validation인지와 관계없이 최종 Decision Threshold 자체를 0.5로 고정하는 것이 기준이다.

**Q3. OOF prediction을 사용하는 것 자체가 금지되나요?**

아니다. OOF를 모델 학습, 앙상블, 성능 분석, 확률 보정 등의 목적으로 활용하는 것은 가능하다. 다만 OOF prediction으로 “이 모델은 0.37에서 F1이 가장 높으므로 Threshold를 0.37로 사용하자”처럼 **최종 Decision Threshold를 결정하는 용도로 쓰는 것은 허용되지 않는다.**

**Q4. Calibration을 적용하는 것은 가능한가요?**

가능하다. 모델이 출력하는 확률값 자체가 더 적절해지도록 학습하거나 보정하는 것은 허용된다. 예:

- Training set 내부의 별도 subset 또는 OOF prediction을 활용한 probability calibration
- Calibration을 고려한 loss 설계
- ECE 등 calibration 관련 정규화 항 추가

다만 calibration 이후에도 최종 label을 결정하는 Threshold는 0.5로 고정되어야 한다. 확률값의 품질을 개선하는 것은 가능하지만, 확률값을 0과 1로 나누는 기준선 자체를 이동시키는 것은 허용되지 않는다.

**Q5. Class마다 서로 다른 Threshold를 사용하는 것은 가능한가요?**

허용되지 않는다. Multi-label classification에서 class별 최적 Threshold를 따로 탐색해 적용하는 것도 Threshold Tuning에 해당한다. 모든 class에 동일하게 0.5를 적용한다.

**정리**

| 구분 | 허용 | 금지 |
|---|---|---|
| Threshold 값 | 모든 class에 0.5 고정 | 0.5 이외의 값(0.4, 0.37, 0.6 등), class별 상이한 값 |
| Threshold 결정 데이터 | — | Train, Train 내부 subset(9:1 등), OOF, Validation 어느 것으로도 조정 불가 |
| OOF | 학습, 앙상블, 성능 분석, 확률 보정 | 최종 Decision Threshold 결정 |
| Calibration | Calibration 사후 보정, calibration-aware loss, ECE 정규화 | 보정 후 Threshold 이동 |

### 3.4 규칙의 안전한 해석

- `label에 따라 상이한 전처리 금지`는 정답 라벨을 미리 보고 샘플별 처리 방식을 바꾸는 행위를 막는 규칙으로 이해할 수 있다.
- `평가 데이터에서만 유리한 특별 전처리 금지`는 validation/test에만 맞춘 수작업 보정이나 데이터 누수를 막는 규칙으로 이해할 수 있다.
- Validation은 공식적으로 허용된 평가·튜닝 용도로 사용할 수 있지만, Validation loss를 직접 최적화하도록 데이터를 학습 배치에 넣어서는 안 된다.
- 공지에서 명시하지 않은 전처리 통계 추정은 Training 데이터만으로 수행하는 것이 안전하다.

### 3.5 아직 확인할 경계 사례

- 오픈소스 음성 인식 모델을 전사 생성에 사용할 수 있는지

## 4. 참고용 기술 후보

### 4.1 발표 슬라이드의 도구 후보(주최측의 힌트)

- KoBERT
- MFCC
- Mel-spectrogram
- Wav2Vec2
- AST (Audio Spectrogram Transformer)
- RandomForest
- ResNet

### 4.2 음성 처리 경로

1. **Raw waveform 기반 특징 추출**
   - `librosa` 등을 이용해 MFCC 또는 Mel-spectrogram 추출
2. **이미지 모델 활용**
   - MFCC 또는 Mel-spectrogram을 2D 이미지처럼 취급
   - ResNet, ViT 등의 이미지 분류 모델 적용 가능
3. **End-to-end 음성 모델 활용**
   - Wav2Vec2, HuBERT, AST 등 음성 특화 모델을 fine-tuning
4. 어느 경로가 어느 Mission에 유리한지는 직접 실험

### 4.3 용어 해설

- **Raw waveform**: WAV 파일에 저장된 시간에 따른 소리 진폭 자체이다.
- **MFCC**: 사람의 청각 특성을 반영해 음색과 발음 특성을 작은 수의 숫자로 요약한 특징이다.
- **Mel-spectrogram**: 시간에 따라 어떤 주파수의 소리가 강한지를 이미지처럼 나타낸 표현이다.
- **End-to-end**: 사람이 MFCC 같은 특징을 미리 설계하기보다, 모델이 원시 음성에서 필요한 표현을 직접 학습하는 방식이다.
- **Fine-tuning**: 대규모 데이터로 미리 학습된 모델을 현재 대회 데이터에 맞게 추가 학습하는 것이다.

발표 슬라이드의 후보는 사용 가능성을 보여주는 참고 목록이며, 특정 모델 사용이 의무라는 뜻은 아니다.

## 5. Mission 1 — 신고자의 성별 분류하기

### 5.1 과제

> 음성으로부터 신고자의 성별을 분류하시오.

### 5.2 입력과 허용 정보

- 입력: 음성 원천데이터
- 라벨링데이터는 학습 시 `startAt`, `endAt`, `Speaker`만 사용 가능
- inference 시 `startAt`, `endAt`, `Speaker`만 사용 가능

공식 PDF에는 학습과 inference 모두 `Speaker`를 사용할 수 있다고 적혀 있다. Zoom 캡처에서는 inference 시 `startAt`, `endAt`만 허용하는 것으로 보였으나, 이메일로 배포된 공식 PDF를 우선한다. 실제 JSON 키의 대소문자는 데이터에서 다시 확인해야 한다.

### 5.3 출력

- 남/여 분류
- 라벨링데이터의 `gender`에 해당

### 5.4 평가 지표

- Accuracy

Accuracy는 전체 평가 샘플 중 정답을 맞힌 샘플의 비율이다.

### 5.5 발표 힌트

- 일정한 길이의 음성을 입력받는 모델을 사용하려면 짧은 음성은 padding할 수 있다.
- 긴 음성은 적절한 stride로 sliding window를 적용하는 등의 전처리가 유용하다.

### 5.6 구현 시 주의점

- 발화 길이가 다르므로 고정 길이 입력을 사용할 경우 padding, crop, sliding window 중 하나가 필요하다.
- 긴 발화를 여러 조각으로 예측하면 조각별 확률을 평균하거나 다수결하는 집계 규칙이 필요하다.
- 성별 클래스 비율이 불균형하면 Accuracy만으로 내부 모델을 비교할 때 소수 클래스를 놓칠 수 있으므로 confusion matrix와 클래스별 recall도 함께 확인하는 것이 좋다. 단, 공식 평가는 Accuracy이다.

## 6. Mission 2 — 신고자/119대원 분류하기

### 6.1 과제

> 주어진 음성이 신고자의 발화인지 119대원의 발화인지 분류하시오.

### 6.2 입력과 발화 조각의 정의

- 입력: 한 사람의 한 발화 조각
- 조각의 기준은 라벨링데이터의 `startAt`, `endAt`으로 정한다.

### 6.3 사용 금지 정보

- `startAt`, `endAt` 이외의 annotation은 사용할 수 없다.
- text도 사용할 수 없다.
- 발화의 홀짝 등 순서 정보를 사용할 수 없다.

### 6.4 출력

- 신고자: `speaker=1`
- 119대원: `speaker=0`

### 6.5 평가 지표와 제출

- 평가 지표: Accuracy
- 참가자는 학습 완료된 모델과 추론 코드를 함께 제출

### 6.6 구현 시 주의점

- 대화 순서를 사용하지 못하므로 각 음성 조각만 보고 판단해야 한다.
- text를 사용할 수 없으므로 음성 인식 결과나 전사 문장의 키워드로 구분하는 방식은 규칙 위반 가능성이 높다.
- 신고자와 119대원의 음향 환경, 말투, 억양, 감정 상태, 통화 채널 특성 등이 모델 단서가 될 수 있지만, 특정 파일명·녹음 순서 같은 우회 정보에 의존하지 않는지 점검해야 한다.

## 7. Mission 3 — 환자의 증상 인식

### 7.1 과제

> 대화로부터 환자의 증상을 인식하시오.

### 7.2 입력과 허용 정보

- 입력: 신고자 및 119대원의 대화 텍스트(라벨링데이터)
- 전사 텍스트 외 라벨링데이터는 사용할 수 없다.

### 7.3 출력

- 출력: 환자의 증상, 즉 라벨링데이터의 `symptom`
- 한 샘플의 증상 개수는 0개부터 9개까지일 수 있다.
- `symptom` 클래스는 string type으로 처리한다.

### 7.4 평가 대상 9개 증상

1. 고열
2. 구토
3. 두통
4. 복통
5. 어지러움
6. 열상
7. 오심
8. 전신쇠약
9. 호흡곤란

### 7.5 대상 외 증상 처리

- 데이터의 symptom list에 위 9개 이외의 symptom이 포함된 경우, 해당 symptom은 평가 대상에서 제외한다.
- 전처리 과정에서 9개에 해당하지 않는 label만 symptom list에서 제거한다.
- 샘플 전체를 제거하는 것은 아니다.

예를 들어 원래 증상이 다음과 같다면:

```text
["두통", "복통", "찰과상"]
```

9개 평가 클래스에 포함되는 다음 두 증상만 string type으로 출력해야 한다.

```text
["두통", "복통"]
```

### 7.6 평가 지표

- 증상 종류별로 F1-score를 따로 계산한 뒤 평균내는 방식을 사용한다.
- 공식 PDF 10쪽은 각 증상을 이진 레이블로 변환한 뒤 레이블별 TP/FP/FN을 집계하고, 클래스별 F1-score를 평균내는 예시를 제시한다.
- 예시에서는 세 클래스의 F1-score가 `0.67`, `0.67`, `0.00`일 때 Macro 평균을 `(0.67 + 0.67 + 0.00) / 3 = 0.44`로 계산한다.

따라서 평가 구조는 **클래스별 F1-score의 Macro 평균**으로 확정한다.

**[추가 확인 필요]** 공식 PDF에도 다음 구현 세부사항은 제시되지 않았다.

- ~~예측 확률을 label로 바꾸는 임계값~~ → 공식 Q&A로 확정: **0.5 고정** (3.3.1 참조)
- 정답 또는 예측에 양성 샘플이 전혀 없는 클래스의 처리
- 출력 문자열의 정확한 구분자·따옴표·정렬 규칙

### 7.7 문제 유형 해설

이 Mission은 일반적인 다중 클래스 분류가 아니라 **다중 레이블 분류**이다. 한 대화에 `두통`과 `복통`이 동시에 존재할 수 있으므로, 9개 증상을 각각 독립적인 0/1 예측 문제로 취급하는 방식이 자연스럽다.

모델 출력의 일반적인 형태는 9개의 확률이다.

```text
[P(고열), P(구토), ..., P(호흡곤란)]
```

각 확률에 **0.5 임계값(≥ 0.5 → 1, < 0.5 → 0)을 모든 증상에 동일하게 적용**해 최종 증상 목록을 만든다. 임계값 튜닝(클래스별 포함, Train/OOF/Validation 기반 모두)은 금지이며, 확률 품질 개선(calibration)만 허용된다. 자세한 내용은 3.3.1 참조.

## 11. 기존 준비와 비교한 팀 역량 변화

### 11.1 기존 예상과 실제 공개 문제의 차이

기존 출제 경향 분석에서는 2022~2024의 이미지 중심 흐름 때문에 이미지 분류와 전이학습을 최우선으로 준비했다. 이번 공개 문제는 그 예상에서 크게 벗어나 **음성 2개 Mission + 텍스트 1개 Mission**으로 구성되었다.

| 구분 | 기존에 집중한 준비 | 이번 문제에서 필요한 역량 | 재사용 가능성 |
|---|---|---|---|
| 데이터 로딩 | 이미지 Dataset/DataLoader | WAV·JSON 로딩, 발화 구간 crop | PyTorch Dataset 구조는 재사용 가능 |
| 전처리 | resize, augmentation | resampling, padding, sliding window, 텍스트 정제 | 실험 통제 원칙은 재사용 가능 |
| 모델 | ResNet18 중심 | 음성 특징+ML, 스펙트로그램 CNN, 음성 사전학습 모델, 텍스트 분류 | ResNet은 스펙트로그램 경로에서 재사용 가능 |
| 평가 | Accuracy, 오분류 분석 | Accuracy 2개, 다중 레이블 F1 1개 | confusion matrix·오류분석 습관 재사용 가능 |
| 재현성 | seed, 고정 split, checkpoint | 동일 + Mission별 단일 추론 명령 | 거의 그대로 재사용 가능 |
| 결과물 | 노트북·실험 로그 | 모델 코드·가중치·requirements·PPT·inference.py | 기존 협업 구조를 확장 가능 |

### 11.2 새로 필요한 핵심 역량

1. WAV 파일과 JSON annotation 구조 이해
2. `startAt`, `endAt` 기준의 발화 구간 추출
3. sample rate 통일과 음성 길이 처리
4. MFCC·Mel-spectrogram 추출
5. Wav2Vec2/HuBERT/AST 계열 사전학습 모델 사용
6. 다중 레이블 텍스트 분류 (임계값은 0.5 고정, F1 기반 임계값 결정 금지)
7. Mission별 금지 annotation을 침범하지 않는 데이터 파이프라인
8. 한 명령으로 동작하는 `inference.py`와 제출 패키징

### 11.3 버리면 안 되는 기존 준비

- 빠른 baseline부터 만들고 한 요소씩 바꾸는 통제 실험
- train/validation 분리와 validation 학습 금지
- random seed 고정
- 체크포인트 저장과 재시작
- 오류 샘플 확인과 slice 분석
- 실험 목적·변경점·결과·결론 기록
- 발표에서 전처리와 모델 선택 이유 설명

즉, 지금까지의 이미지 훈련이 무용해진 것은 아니다. **모델 종류보다 더 중요한 실험·재현성·협업 습관은 그대로 재사용**할 수 있고, ResNet 경험도 Mel-spectrogram 기반 분류에 연결할 수 있다.

## 12. 초기 기술 전략 — 확정안이 아닌 실험 후보

이 절은 공식 문제의 요구사항이 아니라, 데이터를 받은 뒤 비교할 최소 후보군이다.

### 12.1 Mission 1·2 공통 baseline 후보

1. WAV 구간 crop 및 sample rate 통일
2. 짧은 음성 padding, 긴 음성 crop 또는 sliding window
3. MFCC 또는 Mel-spectrogram 추출
4. 빠른 baseline
   - MFCC 통계량 + RandomForest/Logistic Regression
5. 딥러닝 baseline
   - Mel-spectrogram + 작은 CNN 또는 ResNet18
6. 고도화 후보
   - Wav2Vec2/HuBERT/AST fine-tuning

초기에는 복잡한 end-to-end 모델부터 시작하지 말고, 데이터 파이프라인과 평가 코드가 맞는지 확인할 수 있는 빠른 baseline을 먼저 만드는 것이 안전하다.

### 12.2 Mission 3 baseline 후보

1. 전사 텍스트만 추출
2. 평가 대상 9개 이외 label만 제거
3. 9차원 multi-hot target 생성
4. 빠른 baseline
   - TF-IDF + 증상별 Logistic Regression
5. 딥러닝 baseline
   - KoBERT 계열 encoder + 9개 sigmoid 출력
6. 각 증상별 validation F1 확인
7. 임계값은 0.5 고정 (조정 금지, 3.3.1 참조). 확률 품질은 calibration으로만 개선

### 12.3 첫 데이터 수령 직후 우선순위

1. 파일 수·용량·폴더 구조 확인
2. WAV와 JSON 매칭률 확인
3. 허용 필드만 읽는 Mission별 loader 분리
4. 클래스 분포와 발화 길이 분포 확인
5. 공식 metric을 그대로 재현하는 평가 함수 작성
6. 가장 빠른 baseline 생성
7. 오류 분석 후 다음 모델 결정

## 15. 여기서 꼭 이해하고 넘어갈 점

이번 문제는 하나의 거대한 모델을 만드는 문제가 아니다.

- Mission 1과 2는 같은 음성을 쓰지만 **목표와 허용 정보가 다른 별도 분류 문제**이다.
- Mission 3은 음성이 아니라 **허용된 전사 텍스트만 이용하는 9개 증상 다중 레이블 문제**이다.
- 성능 이전에 Mission별 금지 정보가 데이터 파이프라인에 섞이지 않도록 분리하는 것이 중요하다.
- 최종 평가는 모델 성능뿐 아니라 재현 가능한 학습 코드, 한 번에 실행되는 추론 코드, 가중치, 패키지 목록, 결과 PPT까지 포함하는 종합 과제이다.

따라서 첫 구현 목표는 최고 성능 모델이 아니라 **규칙을 지키며 세 Mission을 끝까지 실행할 수 있는 baseline 파이프라인**이어야 한다.
