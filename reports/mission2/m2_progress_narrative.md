# 미션2(대원/신고자 화자 분류) 성능 개선 과정 기록

이 문서는 미션2 정확도를 올리기 위해 우리가 시도한 아이디어, 시행착오, 그리고 현재 진행 상황을 시간 순서대로 정리한 기록이다. PPT/ipynb 작성 시 "학습 과정 및 주요 실험 결과" 항목의 초안으로 바로 활용 가능하다.

## 0. 문제 정의

- 입력: 한 사람의 발화 구간 하나 (`startAt`~`endAt`로 정의된 고립된 utterance)
- 출력: 대원(0) / 신고자(1) 이진 분류
- **핵심 제약** (2026-09-15 주최측 FAQ로 확정): 오직 해당 발화 구간 자체에서만 계산 가능한 정보만 사용 가능. 같은 통화의 다른 발화 정보는 순서 무관 집계값이라도 전부 금지.
- 채점 지표: **정확도(accuracy) 단일 지표**. 클래스별 recall 균형은 채점에 반영되지 않음 → recall gap을 줄이려고 threshold나 class_weight를 조정하는 건 오히려 손해.

## 1단계. L1 베이스라인 구축 (GBM 계열)

53차원 수작업 피처(duration, MFCC40, RMS, ZCR, spectral 계열)로 LightGBM 베이스라인을 만들고, 여기서부터 개선을 시도.

### 성공한 것

| 시도 | 내용 | 결과 |
|---|---|---|
| **하이퍼파라미터 재튜닝** | 기본값(`num_leaves=31, n_estimators=100`)이 826k행 규모에서 과소적합 상태였음. `num_leaves=255, learning_rate=0.02, n_estimators≈1150`(+early stopping)으로 변경 | 84.59% → **86.9%** (+2.3%p, 지금까지 가장 큰 단일 개선) |
| **라벨 오류 수정** | 통화 5건에서 대원/신고자 라벨이 통째로 뒤바뀐 것을 transcript로 확인 후 수정 (`CONFIRMED_LABEL_SWAPPED_CALL_IDS`) | 소폭 개선. 추가 후보 10건은 청취 검증 대기 중 |

### 시도했다가 철회한 것 — call-relative features

`f0_mean`, `rms_p90`, `duration_sec`을 같은 통화 내 평균/표준편차로 z-scoring하는 피처. 내부 테스트에서 +0.1~0.3%p로 작아도 꾸준한 개선을 보여 한때 병합(PR #11)까지 됐지만, **2026-09-15 주최측 FAQ로 "같은 통화의 다른 발화 정보를 어떤 형태로든 쓰면 안 된다"는 규정이 확정되면서 규정 위반으로 판명**. 브랜치에서 제거 완료(2026-09-18, `feature-fixes-clean` 브랜치에 revert 커밋). 정확도 숫자만 보고 규정 확인을 나중에 한 것이 문제였고, 이후로는 "머지 전에 규정부터 확인"을 원칙으로 삼음.

### 막다른 길 (재시도 안 함)

- **절대 pitch/energy 피처** (`f0_mean`, `voiced_ratio` 등 단독 추가): 이미 있는 spectral_centroid/MFCC0과 중복 → 효과 거의 없음(~0.15%p)
- **harmonicity/overlap-detection 피처** (자기상관 피크 기반, 발화 겹침 탐지 목적): 합성 톤에서는 깨끗하게 작동했지만 실제 데이터에서는 겹침 오류율을 오히려 악화시킴(8.38%p → 8.66%p). 합성 테스트가 "동일 음량 겹침"을 가정한 반면, 실제 겹치는 목소리는 음량 차이가 훨씬 불균등해서 가정이 깨진 것으로 추정.

### L1의 결론

손수 설계한 통계 피처(GBM) 방식은 **~85~87%가 사실상 천장**이라는 결론. 특히 발화 길이 편향과 발화 겹침으로 인한 오류는 피처를 더 추가하거나 데이터 양을 늘려도 닫히지 않았음 → 더 나은 개선은 raw 시간-주파수 구조를 직접 보는 모델(CNN, 사전학습 음성 임베딩)이나 실제 음원 분리 같은 오디오 레벨 개선이 필요하다는 판단.

## 2단계. L2 피벗 — Mel-spectrogram + CNN

L1의 천장에 부딪히자, 손수 만든 통계 피처 대신 **mel-spectrogram을 CNN(`SpeakerCNNLarge`, conv block 4개)에 직접 학습**시키는 방향으로 전환. 29,200개 통화 전체 데이터로 학습.

- **결과: 내부 검증 정확도 91.22%** — 목표였던 90%를 돌파.
- 발화 단위 mel-spectrogram만 사용하므로 애초에 "고립 발화" 규정을 위반할 여지가 없음(추가 수정 불필요).

### 여기서 발생한 프로세스 문제

CNN 작업 브랜치(`mission2-l2-cnn`)가 `main`이 아니라 아직 실험 중이던 GBM 피처 브랜치(`mission2-feature-fixes`) 위에서 곧바로 이어붙여져(15개 커밋이 한 줄로 CNN 작업과 피처 작업이 뒤섞임) 만들어짐. 결과적으로 91.22%라는 숫자가 CNN 자체 효과인지, 라벨 수정 효과인지, 데이터 스케일 효과인지 구분이 안 되는 상태가 됨. 확인 결과 다행히 `main` 자체는 오염되지 않았음(PR들의 base가 `main`이 아니라 다른 feature 브랜치였던 것으로 확인) — 하지만 앞으로는 **새 실험 브랜치는 항상 `main`(혹은 현재 검증된 베이스라인)에서 분기**하고, 정확도만으로 병합을 판단하지 않고 "무엇을 고정하고 무엇을 바꿨는지"를 명시한 뒤 병합하기로 규칙을 세움. 이후 CNN 전용 브랜치(`mission2-l2-cnn-clean`)와 피처 전용 브랜치(`mission2-feature-fixes-clean`)를 깔끔하게 분리해 재구성 완료.

### 보류 직전 마지막 시도 — 화자 격차를 겨냥한 CNN 실험 (2026-09-16)

L1 오류 분석에서 확인된 것과 같은 종류의 문제(대원/신고자 recall 격차, 특히 "네"/"예" 같은 0.5~1초 backchannel 발화)가 CNN에도 남아있는지 확인하려고 두 가지를 시도. `mission2-l2-cnn`/`mission2-l2-cnn-clean` 두 브랜치 모두에 반영됨:

- **`SpeakerCNNLargeWithDuration`**: 발화 자신의 `duration_sec`(log1p 압축, 스펙트로그램 인덱스에 이미 존재하는 값 — 다른 발화 정보를 끌어오는 게 아니라 규정 위반 아님)을 classifier head에 명시적으로 추가 입력. 의도는 3번의 MaxPool(stride 2) 이후 짧은 발화가 남기는 프레임 수가 거의 없어지는 문제를 duration 정보로 보완하는 것. **결과: 전체 정확도는 +0.30%p 개선됐지만, 대원/신고자 recall 격차는 오히려 8.45%p → 9.17~9.35%p로 소폭 벌어짐**(Colab 실행 기준). 이 방향은 격차를 줄이지 못함 — 기존 91.22% 체크포인트/학습 경로는 그대로 두고 별도 클래스로만 추가.
- **`--hop-length`**: 다른 메커니즘을 겨냥 — `HOP_LENGTH=160` 기준 짧은 발화가 1~2 타임스텝까지만 살아남는 문제를, hop_length를 절반으로 줄여 프레임 수를 약 2배로 늘려서(스모크 테스트로 16→31, 76→151 프레임 확인) 완화하려는 시도. 기존 91%+ 체크포인트가 의존하는 스펙트로그램은 건드리지 않고 별도 `--output-dir`에 고해상도 스펙트로그램을 새로 만드는 인프라만 추가한 상태 — **2026-09-19 기준 이 설정으로 재학습/평가는 아직 하지 않음** (미평가 상태로 L2가 보류에 들어감).

## 3단계. 우선순위 결정 — L1 먼저, L2는 보류

2026-09-18, 정확도는 L2(91.22%)가 훨씬 높지만 **베이스라인(L1)부터 제대로 완성하는 것이 우선순위**라는 판단 하에 L2 CNN 작업은 잠정 보류. 이후 L1 쪽에 집중:

- 모델 비교 전용 브랜치(`mission2-l1-model-comparison`)를 새로 만들어 GaussianNB / LogReg / RandomForest / XGBoost / LightGBM을 동일 split(GroupSplit, seed=42)으로 공정 비교하는 스크립트 작성.
- 규정 위반 피처(call-relative)는 이 브랜치에서 완전히 제거되어 다시 순정 53차원 피처셋으로 복귀.

### 모델 비교 결과 (2026-09-18)

826,333발화 전체, 동일 `GroupShuffleSplit(seed=42)`로 공정 비교. 1차 실행에서 XGBoost/RandomForest만 `n_estimators=300`, LightGBM은 기본값(100그루)으로 돌려서 생긴 불공정 비교를 발견하고, 트리 개수를 300으로 통일해 재실행:

| 모델 | Accuracy | 대원 recall | 신고자 recall | 격차(신고자−대원) |
|---|---|---|---|---|
| LightGBM 기준선(n=100, 기본값) | 84.59% | 79.75% | 89.08% | 9.33%p |
| GaussianNB | 69.70% | 80.96% | 59.26% | −21.70%p(역전) |
| 로지스틱회귀 | 83.24% | 79.53% | 86.68% | 7.14%p |
| RandomForest(n=300) | 84.05% | 81.17% | 86.72% | 5.55%p |
| LightGBM(n=300) | 86.00% | 81.36% | 90.30% | 8.94%p |
| XGBoost(n=300) | 86.47% | 82.17% | 90.44% | 8.27%p |
| **LightGBM 튜닝**(num_leaves=255, lr=0.02, n=1150, early stopping) | **86.77%** | 82.04% | 91.16% | 9.12%p |

- XGBoost가 기준선보다 좋아 보였던 것(+1.88%p)의 대부분(75%)은 "모델 차이"가 아니라 "트리 개수 차이"였음 — 트리 수만 300으로 맞춰도 LightGBM이 84.59%→86.00%로 따라옴. 그 위에서 LightGBM을 제대로 튜닝하면 XGBoost(86.47%)를 다시 앞섬(86.77%) → **"어떤 모델이냐"보다 "얼마나 제대로 튜닝했냐"가 더 큰 변수**.
- 1단계에서 (규정 위반 피처가 섞여 있던 64차원 기준으로) 검증됐던 튜닝 조합(84.59%→86.9%)이, 규정 위반 피처를 제거한 순정 53차원에서도 거의 동일한 개선폭(84.59%→86.77%)으로 재현됨 → 그 튜닝이 피처 오염과 무관하게 진짜로 유효했다는 것을 재확인.
- RandomForest는 트리 수를 맞춰도 부스팅 계열(86.00%/86.47%)에 못 미치고 학습 시간은 가장 김(14분, LightGBM의 약 80배) → 우선순위 낮음. GaussianNB/로지스틱회귀는 예상대로 하한선/선형성 기준점 역할만 함.
- **최종 L1 후보로 LightGBM 튜닝(86.77%, threshold=0.5, class_weight 없음)을 확정** — 아래 4단계 표의 "내부 split 86.77%"가 바로 이 숫자.

### 대원 recall 밀어보기 — threshold/class_weight 스윕, 최종 기각 (2026-09-18)

위 LightGBM 튜닝 모델(격차 9.12%p)을 대상으로 대원 recall을 올릴 수 있는지 threshold 스윕(0.5→0.75)과 class_weight 스윕(1.0→3.0)을 시도. (1차 시도는 threshold를 반대 방향(0.5→0.25)으로 낮춰서 의도와 정반대로 신고자 recall만 더 올라가는 실수가 있었고, 방향을 바로잡아 재실행함.)

- 두 방법 다 대원 recall을 올리면 신고자 recall이 거의 대칭적으로(제로섬에 가깝게) 깎이는 트레이드오프로 확인됨. 예: threshold=0.55 → 대원 +2.93%p, 신고자 −3.10%p, 전체 정확도는 오히려 −0.20%p(86.77%→86.57%). class_weight=1.2도 비슷한 수준(대원 +2.41%p, 정확도 −0.08%p).
- 균형점(격차 ≈ 0)은 threshold 0.55~0.60 사이, class_weight 1.2~1.3 사이로 대략 특정됨. 하지만 **대회 채점이 accuracy 단일 기준으로 확정돼 있어서(0단계) 대원 recall을 밀어붙일 채점상의 이유가 없음** — 이 실험의 결론은 "적용하지 않는다": 기본 threshold=0.5, class_weight 없음(86.77%)이 정확도가 가장 높으므로 그대로 최종 L1 후보로 유지.
- 즉 이 실험은 "구조적 원인을 고친 것"이 아니라 "어느 쪽 오답을 더 봐줄지 트레이드오프를 옮겨본 것"이었고, 정확도 단일 기준에서는 옮길 이유가 없다는 것만 확인하고 종료.

## 4단계. 공식 Validation셋 검증 (2026-09-18)

그동안 모든 정확도 숫자는 Training 데이터를 자체적으로 쪼갠 internal split 기준이었고, **주최측이 제공한 진짜 Validation셋(3,640개 통화)은 한 번도 실제로 채점에 써보지 않은 상태**였음(의도적으로 분포도 들여다보지 않고 아껴둠). 최종 후보를 확정하는 시점이라 판단해 처음으로 공식 Validation 전체(111,947개 발화)에 대해 평가만 진행(재학습 없음).

| | 내부 split (Training 20%) | 공식 Validation (전체 3,640통화) |
|---|---|---|
| 정확도 | 86.77% | **86.40%** |
| 대원(0) recall | 82.04% | 81.68% |
| 신고자(1) recall | 91.16% | 90.77% |

내부 split 대비 -0.37%p밖에 차이 나지 않음 → 내부 split 성능이 부풀려진 게 아니라 실제로 처음 보는 데이터에도 잘 일반화된다는 것을 확인. 이 과정에서 로컬 전체 데이터셋 경로가 `C:\dcc_data_local_full`(OneDrive의 "대학부 데이터" 폴더는 Validation이 424개 통화만 있는 불완전한 사본)이라는 것도 함께 정리됨.

## 5단계. 팀원(yeonwoo) 트랙과 비교

팀원 wldusdn03(yeonwoo)이 독립적으로 만든 트랙도 검토:

- MFCC40 단독 + LogisticRegression, 처음부터 공식 Validation으로만 평가
- 베이스라인 80.91% → 여러 피처(스펙트럴 롤오프, ZCR, 센트로이드) 조합 실험 끝에 **81.31%**까지 개선
- **우리 L1(86.40%)이 공식 Validation 기준으로 +5.09%p 앞섬** — yeonwoo가 추가한 피처들은 이미 우리 53차원 피처셋에 다 포함돼 있어서 따로 병합할 실익은 적음
- 다만 yeonwoo의 **Stage1(소규모 타당성 검증) → Stage2(전체 데이터 랭킹) → 단일 후보 사전확정 → 공식 Validation 1회 평가**라는 엄격한 절차, 그리고 "자동으로 승자를 고르지 않고 사람이 결정 셀을 직접 작성"하는 방식은 우리보다 더 견고함 → 앞으로 공식 Validation을 다시 체크할 일이 생기면 이 방식을 차용하기로 함.

## 현재 상태 요약 (2026-09-19 기준)

- **L1 (LightGBM, 튜닝 완료, threshold=0.5, class_weight 없음): 공식 Validation 86.40%로 확정된 현재 베이스라인 후보.** 규정 위반 피처 제거 완료, 라벨 오류 일부 수정 완료. GaussianNB/로지스틱/RandomForest/XGBoost 대비 공정 비교(트리 개수 통일) 완료 — 이 조합(86.77%, 내부 split)이 후보 중 최고임을 재확인. threshold/class_weight로 대원 recall을 밀어보는 실험도 마쳤고, accuracy 단일 채점 기준상 이득이 없어 **적용하지 않기로 최종 결론**(`mission2-l1-model-comparison` 브랜치, 아직 `main` 미병합).
- **L2 (CNN, mel-spectrogram): 내부 검증 91.22%로 L1보다 우수하지만, 사용자 결정으로 잠정 보류 중.** 규정 위반 소지 없음, 아직 공식 Validation 미검증, `main`에도 미병합(PR #17은 병합 없이 닫힘). 보류 직전 화자 격차를 줄이려던 두 실험 중 duration-conditioning(`SpeakerCNNLargeWithDuration`)은 격차를 오히려 소폭 키움(기각), hop-length 절반 축소는 인프라만 만들어두고 **아직 평가 전 상태로 보류에 들어감** — 재개 시 가장 먼저 확인할 항목.
- 다음 결정 포인트: L1 베이스라인을 어느 선까지 다듬고 나서 L2 재개/공식 검증/병합을 할지 — 아직 미정.
