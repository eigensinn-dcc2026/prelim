# Mission 2 baseline(L1) 오류 분석

**기준 모델**: `scripts/train_mission2_baseline.py` (음향 통계 53차원 + LightGBM 기본 파라미터)
**기준 데이터**: 서울/Training 전체 29,200통화 (889,358발화, feature 추출 성공 826,333발화)
**검증**: `call_id` 기준 GroupShuffleSplit(seed=42, test_size=0.2), val 164,983발화
**전체 정확도**: **84.59%** (leakage gap −0.05%p — random split과 거의 차이 없어 화자 암기 없이 진짜 일반화된 결과로 신뢰 가능)

## 0. 데이터 규모별 실험 경과

같은 파이프라인을 통화 수만 바꿔가며 3번 돌렸다. "데이터를 늘리면 정확도가 오르는가"부터 먼저 확인하기 위함.

| 통화 수 | GroupSplit 정확도 | Leakage gap | 대원 recall | 신고자 recall |
|---|---|---|---|---|
| 3,000 | 83.78% | +0.64%p | 79.42% | 87.85% |
| 9,000 | 84.90% | −0.28%p | 80.51% | 88.94% |
| **29,200(전체)** | **84.59%** | **−0.05%p** | 79.75% | 89.08% |

3,000→9,000에서는 데이터를 늘린 만큼(+1.12%p) 개선됐지만, 9,000→전체(3.2배 더 늘림)에서는 오히려 소폭 하락했다(val이 16만 건대라 표준오차 ±0.09%p 수준 — 우연이라기엔 큰 차이). LightGBM을 기본 파라미터 그대로 썼기 때문에, 데이터 규모가 이만큼 커진 만큼 트리 개수/깊이 등을 재조정하지 않은 게 원인일 가능성이 있다. **어떤 규모에서도 대원-신고자 recall 격차(8~9%p)는 거의 그대로**라는 점이 가장 중요한 관찰이다 — 아래에서 다룬다.

## 1. 오류의 공통점 3가지

전체 오류(val 25,419건, 오류율 15.41%)를 세 가지 축으로 쪼개 봤다.

### 1-1. 발화 겹침 — 오류의 57.3%가 여기서 나온다

| | 정확도 | 발화 수 |
|---|---|---|
| 안 겹침 | 88.27% | 92,508 |
| **겹침** | **79.90%** | 72,475 |

겹친 발화는 전체의 43.9%인데, 전체 오류의 **57.3%**를 차지한다(오류율 기준 약 1.7배). 대원(83.37%→75.28%, −8.09%p)과 신고자(92.66%→84.36%, −8.31%p) 양쪽 모두 비슷한 폭으로 깎이므로, **겹침은 두 클래스에 공평하게 손해를 주는 요인**이지 화자 비대칭의 원인은 아니다.

> 학습 데이터에서 겹친 발화를 제외/가중치 조정하는 실험을 이미 진행했으나(3절 표 참고) 효과가 없었다 — 이 손해는 "학습이 오염돼서"가 아니라 val의 그 발화 자체가 물리적으로 두 목소리가 섞여있어서 생기는 것이라, 학습 방식으로는 못 고친다. 오디오/feature 추출 단(음원 분리, 겹침 구간 처리 등)에서 다뤄야 하는 문제다.

### 1-2. 발화 길이 — 0.5~1초 구간이 가장 취약

| 구간 | 정확도 | 발화 수 |
|---|---|---|
| <0.5s | 84.03% | 13,059 |
| **0.5-1s** | **80.00%** | 39,951 |
| 1-2s | 82.54% | 54,403 |
| 2-4s | 88.52% | 39,273 |
| ≥4s | 92.69% | 18,297 |

발화가 길어질수록 대체로 정확해지는데(2-4s, ≥4s에서 뚜렷), **0.5~1초 구간이 오히려 가장 낮다** — 극단적으로 짧은(<0.5s) 발화보다도 낮다. 이 구간이 전체 val의 24%(39,951건)를 차지할 만큼 비중도 커서, 정확도에 미치는 영향이 크다.

화자별로 쪼개면 더 뚜렷하다:

| 구간 | 대원 | 신고자 | 격차(신고자−대원) |
|---|---|---|---|
| <0.5s | 85.54% | 82.68% | **−2.86%p (역전)** |
| 0.5-1s | 71.96% | 86.66% | **+14.70%p (최대)** |
| 1-2s | 78.24% | 87.87% | +9.63%p |
| 2-4s | 85.12% | 91.60% | +6.48%p |
| ≥4s | 87.68% | 95.36% | +7.68%p |

**격차가 0.5~1초에서 최대(14.7%p)이고, 발화가 길어질수록 계속 줄어들다가 가장 짧은 구간(<0.5s)에서는 오히려 대원이 더 높다.** 3,000/9,000통화 규모에서도 동일한 패턴이 나왔었는데, 이번에 전체 데이터(16만 건 이상)로 재확인되어 우연이 아님이 확정됐다.

### 1-3. 화자 비대칭 — 대원이 항상 더 어렵다

| | 정확도 | 발화 수 |
|---|---|---|
| 대원(0) | 79.75% | 79,367 |
| 신고자(1) | 89.08% | 85,616 |

9.33%p 격차. 데이터를 3,000→29,200(약 10배)으로 늘려도 이 격차는 전혀 줄지 않았다 — **데이터 부족이 원인이 아니라 구조적 특성**이라는 뜻이다. 1-2에서 본 duration 패턴과 결합해서 보면: 대원 발화가 통계적으로 더 짧고(맞장구·질문 위주), 그중에서도 애매하게 짧은(0.5~1초) 구간에서 모델이 "신고자"로 편향되게 찍는 경향이 강하다.

### 1-4. 오답도 확신에 차 있다

정답일 때 평균 확신도(predict_proba) **85.43%**, 오답일 때 **67.06%**. 오답 쪽이 낮긴 하지만 50%(순수 반반 추측)와는 거리가 멀다 — 즉 오류 대부분이 "애매해서 찍은" 게 아니라 **모델이 나름 확신을 갖고 틀린 것**이다. 단순 threshold 보정으로는 못 고치는 이유이기도 하다(실제로 M2-EXP-002에서 threshold sweep 결과 최적값이 그대로 0.5로 나왔다).

## 2. 특이 발견: 라벨이 뒤바뀐 것으로 의심되는 통화

발화 3개 이상인 통화 중 정확도가 극단적으로 낮은(5~41%) 상위 10개를 뽑아 예측 패턴을 봤더니, 일부는 "어려워서 틀렸다"가 아니라 **모델이 정답의 정반대를 예측하는 패턴**을 보였다.

| call_id | 정확도(발화 수) | 패턴 |
|---|---|---|
| `651e5550bfd63782eb3866a5` | 5.0% (20) | 대원 10/10, 신고자 9/10이 정반대로 예측됨 — 라벨을 뒤집으면 정확도 95% |
| `651e4b1829d82455557a23b2` | 14.3% (21) | 대원 10/11, 신고자 8/10이 정반대 — 뒤집으면 85.7% |
| `651e49d83f1c5e4f25eec885` | 32.4% (34) | 부분적으로 정반대 패턴 |
| `651e49d83f1c5e4f25eec782` | 33.3% (27) | 부분적으로 정반대 패턴 |

특히 상위 2개 통화는 거의 모든 발화에서 예측이 정답의 반대로 나와서, **원본 라벨의 speaker 값이 통화 단위로 뒤바뀌어 있을 가능성**을 강하게 시사한다. 이건 모델/feature의 한계가 아니라 데이터 자체의 문제일 수 있다는 뜻이라, 팀 차원에서 실제로 확인해볼 가치가 있다.

**제안**: 위 두 call_id의 원본 오디오를 실제로 청음해서 라벨(대원/신고자)이 실제 화자와 맞는지 확인. 맞다면 이 발견은 기각하고 그냥 "매우 어려운 통화"로 분류하면 되고, 틀렸다면(라벨 스왑 확인되면) 이런 통화가 전체 29,200개 중 몇 개나 더 있는지 체계적으로 찾아볼 가치가 있다 — 학습/평가 양쪽에 잡음을 넣고 있는 셈이라 고치면 정확도가 공짜로 오를 수 있다.

## 3. 지금까지 시도해본 것과 결과 (요약)

| 실험 | 결과 | 채택 여부 |
|---|---|---|
| Threshold 보정(0.5 → 다른 값) | 최적값이 그대로 0.5, 개선 없음 | 기각 |
| `class_weight='balanced'` 재학습 | +0.02%p (잡음 수준) | 기각 |
| 겹침 학습 데이터 제외 | −0.25%p (오히려 손해, 데이터 손실이 더 큼) | 기각 |
| 겹침 학습 데이터 가중치 낮춤(0.3x) | +0.14%p (잡음 수준) | 기각 |
| 데이터 3,000→9,000 | **+1.12%p (유일하게 유의미)** | 채택 |
| 데이터 9,000→29,200(전체) | −0.31%p (수확체감/역전) | — |

클래스 불균형 보정과 학습 데이터 필터링 계열은 전부 소진됐다. 데이터 양 늘리기도 이제 한계에 도달했다(9,000에서 이미 정점).

## 4. 다음 방향 제안 (우선순위 순)

1. **라벨 스왑 의심 통화 청음 확인** (2절) — 비용 거의 없고, 맞으면 데이터 품질 문제를 팀 차원에서 바로잡을 수 있음.
2. **하이퍼파라미터 튜닝** — 지금 전체 데이터 규모(89만 발화)에 맞게 LightGBM의 트리 개수/깊이/learning_rate를 재조정. 9,000→29,200에서 정확도가 오히려 떨어진 정황과 직결됨.
3. **Duration/pitch 겨냥 feature 추가** — 0.5~1초 구간의 대원-신고자 격차(14.7%p)를 직접 겨냥. pitch(F0) 통계, 에너지 percentile, 무음 비율 등 현재 53차원에 없는 신호 추가 (별도 브레인스토밍 완료, 우선순위: pitch > 에너지 percentile > delta-MFCC).
4. **겹침 대응은 학습 데이터 쪽이 아니라 feature/오디오 처리 쪽에서** — 음원 분리나 겹침 구간을 고려한 feature 설계가 필요. 단순 제외/가중치로는 안 됨(3절 확인됨).
5. **L2(Mel-spectrogram+CNN)는 후순위** — 4초 이상 구간에서 이미 90%+ 나오는 걸 보면 acoustic 통계 feature의 표현력 자체가 병목은 아님. 위 1~4번이 비용 대비 효과가 더 큼.

## 부록: 재현 방법

```bash
python scripts/analyze_mission2_errors.py \
    --features data/local_cache/m2_features_train_local_full.parquet \
    --index data/local_cache/m2_utterances_train_local_full.parquet \
    --ckpt-path data/local_cache/m2_baseline_lgbm_local_full.pkl \
    --output reports/mission2/m2_error_analysis_full.csv \
    --summary-output reports/mission2/m2_error_summary_full.json
```

`m2_error_analysis_full.csv`(발화 단위 상세, 14MB)는 위 명령으로 재생성 가능해 git에는 올리지 않았다(`.gitignore` 참고). `m2_error_summary_full.json`(요약 수치)만 커밋한다.
